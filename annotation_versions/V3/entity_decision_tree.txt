ENTITY CLASSIFICATION ONLY

Before choosing an entity label:
- Geometry has already been predicted in the separate geometry step.
- Use the predicted geometry to choose the relevant entity branch, but do not let it override clear evidence that the layer meaning belongs elsewhere.
- Classify what the map features primarily represent, not just what attributes they contain.
- Numeric fields are evidence, but they do not automatically make a layer AmountDS.
- If numeric values are attributes of objects, routes, regions, facilities, or reporting units, classify the represented feature first.
- The script may provide entity_evidence and polygon_shape_hints. These are weak supporting evidence only, not labels.
- entity_evidence is meant to ensure all plausible labels are considered. Do not choose the label with the highest keyword count automatically.

Allowed Entity labels:
- ObjectDS
- AmountDS
- ExistenceDS
- EventDS
- PatchDS
- LatticeDS
- ContourDS
- PointMeasuresDS
- CoverageDS
- NetworkDS

==================================================
ENTITY CLASSIFICATION
==================================================

Important entity principle:
- Classify what the map features primarily represent.
- Many object, network, lattice, coverage, contour, patch, and event datasets contain numeric fields.
- Choose AmountDS only when the numeric magnitude itself is the main mapped phenomenon.
- Do not choose AmountDS merely because the dataset has counts, totals, percentages, capacities, scores, identifiers, codes, or other numeric columns.
- Treat entity_evidence as weak evidence and branch-check support only.
- Clear metadata, layer meaning, MapDescription, layer name, and branch questions take precedence.

--------------------------------------------------
PRIORITY ENTITY CHECKS
--------------------------------------------------

Use these checks before ObjectDS/PatchDS reasoning.

Q1. Is the dataset mainly about a route system, street system, transport system, utility system, connected line infrastructure, connections, links, or flows between places?

Examples:
- roads
- streets
- tram lines
- metro lines
- cycling routes
- shipping routes
- pipelines
- heating/cooling transport lines
- cables
- waterways as connected transport infrastructure

Yes -> ENTITY = NetworkDS
No  -> continue

Q2. Is the dataset mainly about something that happened, occurs, changes, or unfolds in time?

Examples:
- incidents
- events
- construction activities
- temporary closures
- observations tied to occurrence time
- trajectories or movements over time

Yes -> ENTITY = EventDS
No  -> continue

Q3. Is the dataset mainly a measurement layer where point locations sample a continuous phenomenon?

Examples:
- air quality measurement stations or sampled values
- noise measurements at locations
- temperature, pollution, groundwater, or other environmental measurements sampled at points

Yes -> ENTITY = PointMeasuresDS
No  -> continue

Note:
- AmountDS is not a global priority check.
- Evaluate object/network/lattice/coverage/contour/patch meaning first.
- AmountDS is checked inside the relevant geometry branches only after asking what the features represent.

--------------------------------------------------
BRANCH A — POINTS OR ICONS
--------------------------------------------------

Q4. What does each point primarily represent?

A. A distinct, countable, real-world thing, place, facility, asset, address, organization, or named object
B. A measurement of a continuous phenomenon at that location
C. Presence/absence of a phenomenon at that location
D. Something that happened or occurred at that location
E. A numeric amount/count/quantity/rate where the amount itself is the main mapped phenomenon
F. None of the above

If A -> ENTITY = ObjectDS
If B -> ENTITY = PointMeasuresDS
If C -> ENTITY = ExistenceDS
If D -> ENTITY = EventDS
If E -> continue to Point Amount check
If F -> ENTITY = ObjectDS as fallback, unless another rule is clearly better

Q5. Point Amount check: is the point layer mainly mapping a numeric magnitude rather than mapping point objects that merely have numeric attributes?

Examples that should be AmountDS:
- counts or totals shown as point values
- capacities where the capacity is the main phenomenon
- rates, percentages, scores, or quantities assigned to locations as the main message of the layer

Examples that should usually remain ObjectDS:
- polling stations with vote totals
- schools with pupil counts
- charging stations with capacity attributes
- facilities with usage numbers
- addresses or locations with numeric identifiers

Yes -> ENTITY = AmountDS
No  -> ENTITY = ObjectDS

BRANCH B — REGIONS
--------------------------------------------------

Q4. Are the regions reporting/statistical/administrative units used to aggregate, report, compare, index, or attach attributes?

Typical examples:
- neighbourhoods
- districts
- boroughs
- postcode areas
- census areas
- statistical zones
- grid cells used as reporting units
- administrative subdivisions

Yes -> ENTITY = LatticeDS
No  -> continue

Q5. Does the dataset provide a full-area thematic classification or homogeneous category field?

Typical examples:
- land use
- zoning
- functional mix
- urban function categories
- ground-use classifications
- area-wide policy/function classes
- exhaustive thematic category polygons

Yes -> ENTITY = CoverageDS
No  -> continue

Q6. Does each region represent an interval, band, class range, contour zone, isoline-like value class, or distance/time band?

Examples:
- noise contour zones
- flood-depth bands
- distance bands
- isochrone areas
- elevation or value intervals

Yes -> ENTITY = ContourDS
No  -> continue

Q7. Does the region depict identifiable real-world objects, places, managed assets, projects, facilities, or named bounded entities?

Choose ObjectDS when the polygon is the thing being mapped.
A useful check: if the polygon were cut in half, would each half no longer be that same feature/object/project/place?
If yes, that supports ObjectDS.

Examples:
- parks
- protected cityscapes treated as named managed areas
- facilities
- buildings
- monuments
- named areas treated as objects
- managed green spaces
- project objects
- housing projects or development sites treated as discrete projects
- bridges, assets, schools, or other named managed entities represented as polygons

Yes -> ENTITY = ObjectDS
No  -> continue

Q8. Does each region represent Boolean presence/absence of a phenomenon?

Use ExistenceDS when the main meaning is simply whether something exists or is present in those places.
Do not use ExistenceDS if the polygons are better understood as selected bounded zones, policy areas, affected areas, or patches of a phenomenon.

Yes -> ENTITY = ExistenceDS
No  -> continue

Q9. Is the region a bounded selected area, zone, patch, applicability area, or occurrence area of a phenomenon, without being a reporting unit, full coverage classification, contour band, or object?

Choose PatchDS when the polygon is not the main object itself, but an area where something applies.
A useful check: if the polygon were cut in half, would each half still be part of the same kind of zone/affected area/policy area/phenomenon extent?
If yes, that supports PatchDS.

Use PatchDS when:
- polygons are selected bounded areas rather than an exhaustive full-area classification
- polygons mark special zones, restriction areas, affected areas, policy areas, risk areas, influence areas, attention areas, buffers, or phenomenon patches
- the layer shows where a phenomenon applies, but the areas do not form a complete thematic coverage
- the area is selected because a condition, policy, restriction, or phenomenon applies there

Yes -> ENTITY = PatchDS
No  -> continue

Q10. Region Amount check: is the region layer mainly mapping a numeric magnitude rather than mapping regions that merely have numeric attributes?

Examples that should be AmountDS:
- polygon values where the numeric amount/rate/score is the main phenomenon
- density, percentage, capacity, forecast, total, or intensity layers where the number is the reason the region is mapped
- thematic numeric value maps that are not merely reporting-unit attributes

Examples that should usually not be AmountDS:
- neighbourhoods, districts, postcode areas, or grid cells with statistics -> LatticeDS
- housing projects with dwelling counts -> ObjectDS
- selected zones with numeric attributes -> PatchDS
- full-area land-use or function classes with codes -> CoverageDS
- contour/value bands -> ContourDS

Yes -> ENTITY = AmountDS
No  -> PatchDS as fallback for bounded non-object regions

--------------------------------------------------
OBJECTDS VS PATCHDS SUPPORTING TESTS
--------------------------------------------------

Use this section only after ruling out the stronger labels above it, especially NetworkDS, EventDS, PointMeasuresDS, LatticeDS, CoverageDS, ContourDS, and clear AmountDS cases.

Core distinction:
- ObjectDS means the feature is the mapped thing.
- PatchDS means the feature is an area where a condition, policy, restriction, phenomenon, or applicability rule holds.

Conceptual divisibility test:
- If cutting the polygon in half would usually destroy the identity of the feature, this supports ObjectDS.
  Examples: a building, monument, school, bridge, facility, named managed asset, housing project, project site, or park treated as a managed place.
- If cutting the polygon in half would still leave two parts of the same kind of area, this supports PatchDS.
  Examples: a restriction area, affected area, risk area, policy area, environmental zone, influence area, attention area, or phenomenon extent.

How to use calculated evidence:
- ObjectDS keyword signals support ObjectDS only when the terms point to concrete things, assets, facilities, places, or projects.
- PatchDS keyword signals support PatchDS only when the terms point to zones, areas of effect, restrictions, policies, risks, buffers, or phenomenon extents.
- polygon_shape_hints.shape_hint = more_object_like supports ObjectDS only weakly; it usually means many compact polygon features.
- polygon_shape_hints.shape_hint = more_patch_like supports PatchDS only weakly; it usually means large area spread, low compactness, or high boundary complexity.
- LatticeDS and CoverageDS signals should push you back toward LatticeDS or CoverageDS before ObjectDS/PatchDS.

Never use geometry-derived hints as a hard rule:
- Some real objects are irregular, such as parks, protected cityscapes, managed green spaces, and development sites.
- Some patches can be compact.
- Metadata and the meaning of the layer are more important than compactness or area statistics.

==================================================
FINAL FALLBACK RULES
==================================================

If the dataset is mainly about:
- connected infrastructure, routes, roads, transport lines, utility lines, or flows -> NetworkDS
- something that happens or unfolds in time -> EventDS
- measured values of a continuous phenomenon at sampled point locations -> PointMeasuresDS
- aggregated reporting units / statistical zones -> LatticeDS
- full-area categorical field or exhaustive thematic coverage -> CoverageDS
- interval/band/isoline representation of a field -> ContourDS
- identifiable real-world bounded things, facilities, assets, places, or projects -> ObjectDS
- Boolean presence/absence -> ExistenceDS
- bounded selected area / special zone / phenomenon patch -> PatchDS
- quantities / totals / counts / densities / rates / percentages / capacities / forecasts / flows as the main mapped phenomenon -> AmountDS

Important distinction rules:
- VectorTessellation is a Geometry label, not an Entity label.
- CoverageDS is for full-area thematic classifications or exhaustive thematic coverage.
- LatticeDS is for reporting/statistical units, even when they contain numeric statistics.
- ContourDS is for interval, contour, isoline, isochrone, or value-band representations.
- PatchDS is for selected bounded phenomenon areas, applicability areas, affected areas, policy areas, or restriction zones, not for every polygon.
- ObjectDS is for real-world objects, places, projects, facilities, assets, or managed entities, even if represented as polygons and even if they have numeric attributes.
- ObjectDS vs PatchDS: ObjectDS means the feature is the mapped thing; PatchDS means the feature is an area where something applies.
- Use the divisibility idea only as a supporting test: objects lose their identity when arbitrarily split; patches/zones usually remain parts of the same area type when split.
- NetworkDS should be preferred over ObjectDS and AmountDS for connected line systems, route systems, street systems, transport systems, utility systems, and infrastructure networks.
- AmountDS should be used only when numeric magnitude is the main mapped phenomenon.
- Do not use AmountDS merely because numeric columns exist.
- If the feature is a polling station, school, facility, route, project, park, building, or named asset with numeric attributes, classify the feature first instead of choosing AmountDS.
